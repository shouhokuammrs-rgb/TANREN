発行: Claude Design / 2026-08-01
モック: `docs/design/IA再設計 3案.dc.html`(ワイヤー級・3案並列)

---

## 0. 診断 — 何が起きているか

棚卸しの3動線を、**「何を決める行為か」**で読み直すと問題の形がはっきりする。

| 動線 | 行為の性格 | 現状 |
|---|---|---|
| 鍛える | 今この瞬間の実行 | 一本の線として完成。触らない |
| 振り返る | 過去と現在の照合 | **行為はひとつなのに、置き場が4つ**(ホーム内2 + タブ外2) |
| 管理 | 設定という名の異質な3種 | **性質を無視して1枚に縦積み** |

つまり本件は「画面が足りない/多い」問題ではなく、**行為の単位とナビゲーションの単位がずれている**問題。
Phase 2/6/7 で機能が個別に足されるたび、置き場は「空いている所」に決まってきた — その堆積が今の形。

観察ログの「使い方を知っているから困りはしない」は、**問題がないのではなく、学習で吸収されている**ことを意味する。唯一のユーザーが学習済みである以上、体感の痛みは指標にならない。したがって本提案は体感ではなく**行為の単位**を基準に構造を決める。

## 1. 3案共通の決定事項

以下は案の選択に依存しない。3案すべてに含む。

### 1-1. 旧ゴール(want/avoid)の撤去 — P-1
5bゴールゲージが完全上位互換。**削除**。移行データなし(旧タグは読み捨て仕様のため)。

### 1-2. 回復表示の統合 — P-4 / ISS-016
フレッシュネス人体図と回復予測スロットは**同じ問い(いま動けるか)への別解**。片方しか見られていないのは当然で、1コンポーネントに統合する。

- 人体図を主、回復予測を従(部位タップで「あと◯時間」を吹き出し)
- 全身回復済みなら「全部位 回復済み」の1行に畳む(情報量を状態で可変に)
- 色は既存どおり **鈍色 = 回復待ち**。成長の溶鉄と混ぜない

### 1-3. 設定の3群分割 — P-5

| 群 | 内容 | 根拠 |
|---|---|---|
| **1. 日常** | 部位別ゴールゲージ(5b)/ 体重 | 週次〜隔週。最上段に置き、ここだけスクロールなしで届く |
| **2. からだと器具** | 器具 / 筋力キャリブレーション / 怪我・制限 / タイマー / エンジン調整 | 初回か変更時のみ。畳んだアコーディオンで既定は閉じる |
| **3. データ** | クラウドバックアップ / エクスポート・インポート / **全データ削除** | 保全と破壊。全削除は**別画面へ隔離**し2段確認 |

現行の「危険操作が日常操作と同一スクロール上にある」状態を、群の分離で構造的に解消する。

### 1-4. スコープ外の前提
- 鍛える動線(ヒヤリング→実行→サマリー)は不変
- ISS-021(実行画面のメニュー一覧シート)は実行画面内に載る前提。IA側では扱わない
- ISS-020(ログ編集)は独立実装。IA案は**ログ画面までの距離**にだけ責任を持つ

## 2. 3案

### 6a 二軸 — 「鍛える」と「振り返る」で割る

**コンセプト:** 動線の性格でタブを定義し直し、散らばった振り返りを1タブに集約する。

タブ(4): ホーム / 鍛える / **振り返る** / 設定

- **ホーム** = 今日のことだけ(回復ステータス・今日のメニュー・開始CTA)
- **振り返る** = セグメント[成長(既定) / ログ / 写真]。体重チップをヘッダー右に常設
- 過去サマリーはログ詳細から再訪(P-6)

**解決:** P-2(2階層→1階層)/ P-3(体重が設定外へ)/ P-4 / P-6

**何を犠牲にしたか:**
- ログがタブ1発でなくなる(振り返る→セグメント→詳細で3階層)。**ISS-020でログ編集の頻度が上がると最初に痛む場所**
- ホームから成長カードが消える。「ついで見」の機会損失を、タブ常設で埋められるかの賭け
- 「鍛える/振り返る」という抽象ラベルの学習が一度必要(現行の名詞ラベルより読み替えが要る)

**向く条件:** 振り返りを1つの行為として扱い、今後もそこへ機能を足していく前提なら最も伸びる。

---

### 6b 昇格 — 成長をタブ5個目に上げる

**コンセプト:** 現行構造を保ったまま、最も深すぎた成長ビューだけを引き上げる最小変更。

タブ(5・上限): ホーム / 今日のトレ / **成長** / ログ / 設定

- **成長** = 熱の人体図 / 部位グラフ+ゴール進捗 / 写真(セグメント)。体重チップをヘッダーに
- **ホーム** = 回復(統合)+ 今日のメニュー + CTA + 成長1行サマリー(「今週 胸+2.1kg」)

**解決:** P-2 / P-3 / P-4 / P-5

**何を犠牲にしたか:**
- **タブ5枠を使い切る。**今後どんな機能が来てもタブには出せない(拡張余地ゼロ)
- 写真比較は成長タブ内で2階層のまま据え置き(月次のため許容と判断)
- 「ホーム/今日のトレ/成長/ログ」の性格差が曖昧なまま。**分散の根本原因は残り、深さだけを直す対症療法**
- 390px幅で5タブはラベルが窮屈(1タブ約72px)。「今日のトレ」→「今日」など短縮が必要

**向く条件:** 変更コストとリスクを最小にしたい / 現行の使い方が身についていて壊したくない場合。

---

### 6c 一枚 — ホームを振り返りダッシュボードにする

**コンセプト:** タブを3つに削り、「見る」をすべてホームの縦スクロール1枚に集約。タブ切替という探索行為そのものをなくす。

タブ(3): **ホーム** / 鍛える / 設定

ホームの縦順: 回復ステータス → 今日のメニュー+CTA → 体重インライン更新 → 成長ブロック → 直近ログ3件 → 写真比較 → 未判定の鏡チェック

**解決:** P-2(最短)/ P-3(最短)/ P-4 / P-6(到達カードがホームに残留し発見性最大)

**何を犠牲にしたか:**
- ホームが長い。**毎日見る回復が、週次・月次の情報と同じスクロール上に並んで相対的に埋もれる**
- ログ一覧・写真比較に直行できない(ISS-020の動線が3案で最も遠い)
- ホームが将来の機能追加の受け皿になり続け、**「継ぎ足し」再発リスクが最も高い**
- 3タブはナビとしての情報量が乏しく、タブバーの存在意義が薄れる

**向く条件:** ユーザーが1人で「上から下へ読む」習慣を確実に作れるなら最速。複数ユーザーへ広げる予定があるなら不利。

## 4. 判断のための論点(Eiichi向け)

選定は以下の3問に答えれば決まる、と考えています。

1. **ログをどれだけ触るか。** ISS-020(ログ編集)実装後、ログの利用頻度は「毎トレ後」になりますか?
   なるなら 6a のログ3階層は致命的で、6b が有利。ならないなら 6a の集約が効く。
2. **タブ枠を使い切ってよいか。** Phase 9以降に新しいタブ級の機能が来る見込みがあるなら 6b は選べない。
3. **成長を「見に行く」か「目に入る」か。** 意識的に見に行くなら 6a/6b、日々の視界に入れたいなら 6c。

なお **P-2(成長の深さ)と P-3(体重)は、ゴールモデル導入直後で利用実績が浅く未検出の可能性**が棚卸しでも指摘されています。3案いずれも P-3 の解は「設定の外に出す」で共通のため、体重については案の選択に依存せず先行実装が可能です。
