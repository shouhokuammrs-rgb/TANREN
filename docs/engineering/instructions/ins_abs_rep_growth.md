# INS: 自重種目のレップベース成長指標(ISS-018)

- 発行: PM / 2026-08-01
- 対象: Engineer(Claude Code)
- 優先度: 🟡(ドッグフーディングで発覚した成長実感の欠落)
- 関連: DEC-009(主指標e1RM)/ DEC-011(成長ビュー)/ Phase 7構想 §2-2「腹の例外」

## 背景(事象)

腹のログが成長ビューに一切反映されない。原因はバグではなく仕様の穴:

- `sessionE1Rm()` は重量なしセットを明示的にスキップする(自重種目対策として意図した挙動)
- 腹3種目のうち**クランチ・レッグレイズは自重**(`requiredEquipment: ['bodyweight']`)のため、ログを積んでもe1RM点列が生成されず、基準種目にもならない
- 結果: 腹は常に「データ不足(冷えた鉄)」表示

## 方針(Eiichi決定・2026-08-01)

自重種目は**最大レップ数の推移**を成長指標とする。e1RMと2系統併存させる。

## 仕様

### 1. 指標の決定ルール(種目単位)

- 種目マスタの `requiredEquipment` に `'bodyweight'` を含む種目 → **レップ指標**(セッション値 = 記録セット中の最大reps)
- それ以外(ダンベル種目) → 従来どおり **e1RM指標**(変更なし)
- 判定は種目マスタ基準で固定(セット内容で動的に切り替えない。シンプル優先)

### 2. growth.ts の拡張

- `GrowthPoint` に指標種別が伝わる形にする(例: `MuscleGrowth.metric: 'e1rm' | 'reps'`。点列の値フィールドは流用可、命名はEngineer判断で改名可)
- 基準種目選定ロジック(セッション数最多・同数は直近優先)は**指標をまたいで従来どおり比較**する。腹でロシアンツイスト(e1RM)とクランチ(レップ)が混在しても、選定は回数ベースなので変更不要
- 成長率の式は同一: `(last - first) / first`。monthlyRate・色エンコーディング(DEC-011の閾値)もそのまま適用する
  - 注記: レップ成長は高レップ帯で伸びやすく色が熱めに出る可能性があるが、**v1は閾値共通で出す**(実機で違和感があればISS起票して調整。ISS-015と同じ将来課題枠)
- レップ指標にE1RM_REP_CLAMP(12)は**適用しない**(クランチのレンジは15〜25。クランプすると成長が消える)

### 3. UI(成長ビュー/部位カード/グラフ)

- 単位表示: e1RM系は「kg」、レップ系は「回」。グラフY軸・チップ・部位カードの数値ラベルすべて
- 基準種目名の表記は従来どおり。指標が「回」であることが一目でわかること(例: 「クランチ 22回」)
- 人体図の色は §2 のとおり共通ロジックのまま

### 4. テスト

- growth.test.ts に追加: 自重セット(weightなし)のみのセッションからレップ点列が生成されること / 混在部位(腹)で基準種目選定が正しく働くこと / レップ成長率の計算 / クランプ非適用
- 既存e1RM系テストが全通過すること(回帰なし)

## スコープ外

- ゴールモデル(Phase 7)との接続。腹はゴールv1対象外のまま(進捗軸は出さない。成長トレンドのみ表示)
- 加重クランチ等の将来種目対応(マスタに存在しないため考えない)

## 完了条件

- 腹のログ(クランチ/レッグレイズ)が成長ビューに「回」で表示される
- handoff作成 + SSOTのISS-018を対応済みに更新
